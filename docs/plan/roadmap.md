| --------------------------------- | ---------- | ---------------------------------------------------------------- |
| 첫 화면에서 물건을 팔지 않는다    | 5-7 ②      | **랜딩이 카탈로그가 아니다.** M1이 M2보다 앞선다                 |
| 설명 텍스트가 거의 없다           | 4절, 5-7 ③ | 카피가 아니라 **이미지가 콘텐츠**다. 에셋 파이프라인이 초기 과제 |

| 매체가 미정이다                   | 7절        | 상품 모델이 **특정 카테고리에 종속되면 안 된다**                 |
| maker 개념을 열어둔다             | 9절        | 플랫폼 확장의 값싼 보험. M2에서 컬럼만 만들어 둔다               |
| 인스타·스토어를 이어간다          | 5-2        | 사이트가 유일 채널이 아니다. **채널 간 연결**이 과제로 남는다    |

## 플랫폼의 세 면

> 2026-09-05 확정. 「플랫폼」이 무엇을 뜻하는지 정해졌다.

버터웨더에서 플랫폼은 **마켓플레이스가 아니다.** 세 면을 뜻한다.

| 면            | 무엇                                        | 누가 쓰나                      |
| ------------- | ------------------------------------------- | ------------------------------ |
| **고객향**    | 웹사이트                                    | 사는 사람                      |
| **관리자향**  | 상품·주문·콘텐츠를 다루는 페이지            | 이나래·홍설아                  |
| **외부 채널** | 인스타그램, 스마트스토어, 그 밖의 3rd party | 사는 사람이 **먼저 만나는 곳** |

### 이것이 로드맵에 미치는 영향

**1. 관리자향은 마일스톤이 아니라 모든 마일스톤에 따라붙는 축이다.**

상품을 넣으려면 M2에, 주문을 보려면 M3에 관리자 화면이 필요하다. 맨 뒤에 몰아서 만드는 것이 아니라 **각 마일스톤이 고객향·관리자향 두 면을 함께 갖는다.**

**2. 외부 채널은 부록이 아니라 여정의 출발점이다.**

브랜드 문서 6절은 브랜드 경험을 "외부에서부터 웹사이트에 도착하기까지의 여정 전체"로 정의했고, 5-2절은 인스타·스마트스토어를 이어가기로 정했다. **사이트는 유일한 채널이 아니라 도착지다.** M4가 이것을 다룬다.

**3. 여러 만든 주체(maker)를 담는 구조는 플랫폼의 뜻이 아니었다.**

다만 브랜드 문서 2절(편집 확장)과 9절(maker 개념)이 **별도의 이유로** 그 자리를 열어두라고 했다. 「값싼 보험」에는 남기되 근거를 그쪽으로 옮긴다.

## M2 — 물건을 보여준다 ✅ (2026-09-19 완료)

> **끝났다는 뜻** — 코드를 건드리지 않고 상품을 늘릴 수 있다. 대시보드가 아니라 **가게 어드민에서** 사진을 올리고 행을 넣으면 화면에 뜬다.

|             | 이니셔티브       | 무엇을 했나                                                                                      |
| ----------- | ---------------- | ------------------------------------------------------------------------------------------------ |
| **I2.1** ✅ | Supabase 기반    | 프로젝트 `ghrpcggsjgiiitxjqdsw`, publishable 키, client/server 분리                              |
| **I2.2** ✅ | 상품 데이터 모델 | `products` + `product_variants`. **가격·재고를 옵션으로 내렸다** — 옛 레포에서 가장 크게 바꾼 곳 |
| **I2.3** ✅ | 목록·상세 화면   | 첫 화면 격자, `/products/<slug>`. 구조는 옛 레포 계승                                            |
| **I2.4** ✅ | 상품 입력 경로   | `/admin` — 로그인·등록·수정·삭제·사진 업로드. 입력값 최대·최소(`0004`)                           |
| **I2.5** ✅ | RLS              | 공개는 읽기만, 쓰기는 `admin_emails` 의 관리자만 (`0003`). **secret 키를 쓰지 않는다**           |

**계획과 달라진 것 둘.**

- **어드민을 「또는 Supabase 직접 입력」으로 두지 않았다.** 대시보드로 버티면 사진 경로를 손으로 적게 되고 그때마다 규칙이 어긋난다. 화면이 규칙을 지키게 했다.
- **쓰기를 secret 키가 아니라 Auth + RLS 로 열었다.** 옛 레포를 확인하지 않고 `0001` 에 「secret 키로만」이라고 적었던 것을 뒤집었다 (schema.md 4절).

설계와 근거는 [docs/dev/schema.md](../dev/schema.md).

## M3 — 판다

> 목표: **주문과 결제가 끝까지 돈다.** 지금 상세 화면의 `Add to Cart`·`Buy It Now` 는 눌리지 않는다. 그 자리에 실제 기능이 들어간다.
>
> **옛 레포에 설계 문서가 있다** — [`docs/design/checkout-data-model.md`](https://github.com/jerryko570/butter-weather-shop/blob/main/docs/design/checkout-data-model.md) (2026-07-08). `orders`(영수증 표지) + `order_items`(줄들) 구조와 **주문 시점 박제**가 거기 있다. 계승한다 (CLAUDE.md 8절 「계승한다고 말했으면 원본을 연다」).

### I3.1 주문 그릇 ✅

| 스토리                  | 무엇을 했나                                                              |
| ----------------------- | ------------------------------------------------------------------------ |
| `docs/order-schema` ✅  | schema.md 7-3절. 옛 것과 다른 곳은 **옵션** — 우리는 variant 가 있다     |
| `feature/orders-sql` ✅ | `0005` — `orders` · `order_items` · RLS · `mark_order_paid()` · 주문번호 |

**박제(snapshot)가 이 설계의 핵심이다.** 주문한 뒤에 이름이나 가격이 바뀌어도 **영수증은 그때 그대로여야 한다.** 그래서 `order_items` 가 이름·옵션 이름·단가를 복사해 들고, 바뀌어도 되는 것(사진)만 `product_id` 로 이어 본다.

주문번호는 **`YYMMDD-NNNN`** 이다. `id` 가 uuid 라 전화로 불러줄 수 없다.

### I3.2 장바구니 ✅

| 스토리                   | 무엇을 했나                                           |
| ------------------------ | ----------------------------------------------------- |
| `feature/cart-store` ✅  | zustand + persist. **줄의 열쇠가 상품이 아니라 옵션** |
| `feature/cart-screen` ✅ | `/cart` — 담은 것·수량·빼기·배송비                    |

**로그아웃하면 비운다.** 장바구니는 브라우저에 있어 로그인과 무관하게 남는데, 그대로 두면 **다음 사람이 앞사람 것을 물려받는다** (2026-09-22에 실제로 그랬다).

### I3.3 주문서 ✅ / 결제 ⬜

| 스토리                      | 상태                                         |
| --------------------------- | -------------------------------------------- |
| `feature/customer-login` ✅ | 구글·카카오 OAuth. **가입 화면이 없다**      |
| `feature/checkout-form` ✅  | 배송지(카카오 우편번호) · 주문 상품 · 동의   |
| `feature/create-order` ✅   | **가격·배송비를 서버가 다시 읽어 박제한다**  |
| `feature/orders-list` ✅    | `/orders` — 내 주문만 보인다 (RLS)           |
| **`feature/payment`** ⬜    | **남은 것은 이것뿐이다.** 결제사 미정 — 아래 |

**가격을 손님이 정하지 못한다.** RLS 는 「누구의 주문인가」만 보고 「얼마인가」는 보지 않는다. 그래서 화면은 `{ variantId, quantity }` 만 보내고 이름·가격·배송비·합계를 전부 서버가 센다.

**재고는 결제 완료 때 깎는다** — `mark_order_paid()` 가 `where stock >= quantity` 로 빼고, 한 줄이라도 모자라면 전체가 되돌아간다.

**배송비는 3,000원, 상품 합계 5만원 이상 무료.** 규칙은 `lib/shipping.ts` 한 군데에만 있고 화면과 서버가 같은 함수를 부른다.

### I3.4 관리자향 ⬜

| 스토리                 | 내용                                        |
| ---------------------- | ------------------------------------------- |
| `feature/admin-orders` | 주문 목록·상태 바꾸기·송장 (M2 어드민 위에) |

주문이 실제로 들어오기 시작해야 필요해진다. **결제 다음이다.**

### ⬜ 아직 안 만든 것

- **주문 취소** — 손님은 만든 주문을 못 지운다(RLS 에 update·delete 정책이 없다). 결제가 붙으면 필요해지고, 그때 관리자 쪽과 같이 만든다
- **주문 확인 알림** — 카카오 「개인으로 등록」으로 이메일은 받게 됐다. 메일로 보낼지 알림톡으로 보낼지는 결제와 같이 판단한다
- **UX·문구 정리** — 에러 문구가 개발자 말투다. 이나래가 「전체적으로 손봐야 한다」고 했다 (2026-09-22)

**결제사가 정해지지 않았다.** 조사는 끝났고 결정만 남았다 — [payment-providers.md](payment-providers.md).

스키마가 결제사를 모르므로(`payment_provider` · `payment_id` 두 칸뿐) **무엇을 고르든 스키마를 안 고친다.** 나중에 바꿔 끼우는 비용도 크지 않다.

## 열린 결정

로드맵을 더 진행하려면 답이 필요한 것들이다.

1. ~~**첫 화면에 무엇을 두는가**~~ → **해소됨. 첫 화면이 섰다(M1 완료).** 아래는 그때의 기록이다.
   방향은 2026-09-12에 정해졌다: `karactor` + `colorcolour` 쪽.** 둘의 공통점은 첫 화면에서 물건을 보여주지 않고 **분위기와 색이 먼저 오며 텍스트가 거의 없다**는 것이다(karactor는 화면 절반이 린넨 커튼, colorcolour는 회색 배경에 인물과 색만). `sunlovetour`의 컬렉션 성좌나 `REE-COLLECT`의 상품 평면 배치는 이번이 아니다.
   남은 것은 **그 자리에 무엇을 둘 것인가\*\* — 사진인가 색면인가, 무엇을 찍은 사진인가. 물건이 아직 없으므로 여전히 열려 있고 이나래 판정이 필요하다. 브랜드 문서 5-9절(감각의 근본)이 이 판단의 재료다.
2. ~~**플랫폼이 무엇을 뜻하는가**~~ → **해소됨. 고객향 · 관리자향 · 외부 채널 세 면이다. 「플랫폼의 세 면」 참조.**
3. ~~**매체를 언제 정할 것인가**~~ → **해소됨 (2026-09-16).** 카테고리를 **형태**로 나눴다 — 키링·팔찌·목걸이. 소재를 정하지 않고도 상품을 넣을 수 있게 됐고, 실제로 키링 하나가 들어갔다.
4. **카탈로그의 시간 축** (M4) — 9절 보류 항목. 하루의 시각이 출발점으로 확보됐으니 지금 풀 수 있다
5. ~~**손님이 로그인을 해야 사는가**~~ → **해소됨 (2026-09-19). 회원만 산다.** 구글·카카오 OAuth 라 가입이라는 단계가 따로 없다. 아래는 그때의 기록이다.
   옛 레포는 **회원만** 살 수 있었다(`orders.user_id` 가 `not null`). 그래서 주문 내역을 보여줄 수 있고 RLS 가 「자기 주문만」으로 깔끔해진다. 대신 **처음 온 사람이 가입부터 해야 한다** — 키링 하나 사려는 사람에게는 그게 벽이다.
   비회원 주문을 허용하면 그 벽이 없어지지만, **주문을 무엇으로 식별할지**를 따로 정해야 한다(주문번호+전화번호 같은 것). 둘은 스키마가 달라 나중에 바꾸면 주문 데이터를 통째로 손봐야 한다.
6. ~~**재고를 언제 깎는가**~~ → **해소됨 (2026-09-19). 결제 완료 때 깎는다.** 조건부 update 라 읽고 나서 빼는 틈이 없다. 아래는 그때의 기록이다. 결제 완료 때 깎으면 결제 직전까지 남이 살 수 있어 **오버셀링**이 나고, 장바구니에 담을 때 깎으면 안 사고 나간 사람의 재고가 묶인다. 재고가 3개인 핸드메이드라 이 차이가 실제로 문제가 된다.
7. **결제 수단** (M3) ★ — **지금 M3 를 막고 있는 유일한 결정이다.** 조사는 끝났다 — [payment-providers.md](payment-providers.md). `@portone/browser-sdk` 가 의존성에만 있고 아직 안 쓴다. **PortOne 안에서 무엇을 열지**(카드·계좌이체·간편결제) 정해야 하고, 사업자 정보와 정산 계좌가 필요하다. 브랜드 문서 밖의 일이라 이나래 확인이 필요하다.
