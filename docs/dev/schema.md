# 데이터베이스 스키마

확정 SQL은 [`supabase/migrations/`](../../supabase/migrations/)에 있다. **이 문서는 왜 그렇게 짰는지**를 적는다.

> **실행됐다 (2026-09-16).** 프로젝트는 `ghrpcggsjgiiitxjqdsw`(이나래 계정)이고 `products` · `product_variants` · `products_public` 이 서 있다.
>
> 확인한 것 — 셋 다 publishable 키로 조회되고(200), `insert` 는 RLS 가 막고(`42501`), 없는 카테고리(`bead`)는 enum 이 거부한다(`22P02`).
>
> **`0002` 도 실행됐다 (2026-09-19).** `product-images` 버킷이 서 있고, 첫 상품 `flower-garden-keyring` 의 사진 5장이 공개 주소로 열린다(200).
>
> **첫 상품이 끝까지 통과했다** — 대시보드에서 올린 사진과 넣은 행이 코드 수정 없이 화면에 나왔다. `products_public` 에 최저가 11,900 · 총재고 9 · 옵션 3 으로 잡힌다.

## 0. 옛 레포에서 계승한다

[`jerryko570/butter-weather-shop`](https://github.com/jerryko570/butter-weather-shop)에 이미 돌아가는 스키마가 있었다. `src/types/product.ts`가 실제 테이블 컬럼과 1:1로 적혀 있어 그대로 읽을 수 있었다. 디자인을 계승한 것과 같은 이유로 **데이터 모델도 계승한다.**

**다만 옛 쪽은 테이블을 Supabase 대시보드에서 손으로 만들어 재현할 방법이 없었다.** 프로젝트가 날아가면 기억으로 다시 만들어야 한다. 여기서는 `.sql` 파일로 남긴다.

## 1. 가장 크게 바꾼 것 — 옵션이 테이블이 됐다 ★

옛 쪽은 이랬다.

```ts
options: string[]   // ['그린','블루']
price_krw: number   // 상품에 하나
stock: number       // 상품에 하나
```

**이 구조로는 옵션마다 가격과 재고를 다르게 둘 수 없다.** 이나래의 요건이 그것이라(2026-09-16) 옵션을 테이블로 올렸다.

```
products            — 「물건」. 이름·설명·사진·카테고리
product_variants    — 「파는 단위」. 가격·재고
```

**가격과 재고가 `products`에 없다.** 그것은 파는 단위의 성질이지 물건의 성질이 아니다. 같은 팔찌라도 14cm와 16cm는 값과 남은 수가 다르다.

### variant 가 없는 상품은 팔 수 없다

옵션이 하나뿐인 물건도 **variant 를 하나 만든다** (이름은 `기본` 등).

번거로워 보이지만 이유가 있다 — **가격과 재고가 두 군데에 있으면 반드시 어긋난다.** 「variant 가 있으면 variant 값, 없으면 상품 값」 같은 규칙은 코드 여기저기에 흩어지고 언젠가 한쪽만 고쳐진다. 한 군데로 모은다.

제약으로 강제하지는 않았다. 대신 `products_public` 뷰가 variant 없는 상품을 **자동으로 걸러낸다.** 실수로 만들어도 손님에게 안 보인다.

## 2. products

### 카테고리는 형태다

```sql
create type product_category as enum ('keyring', 'bracelet', 'necklace');
```

2026-09-16 확정 (foundation.md 8절 1번). 옛 쪽은 `'keyring' | 'bead' | 'etc'`였는데 **`bead`는 소재 이름**이었다. 지금은 형태로 나눈다 — 비즈로 만들지 않은 팔찌가 나와도 카테고리는 그대로다.

**`etc`를 두지 않는다.** 빈 칸이 있으면 애매한 것이 거기로 밀려나 분류가 흐려진다. 형태가 다른 것이 나오면 그때 enum 값을 늘린다.

> `text`가 아니라 enum 인 것은 **값을 늘릴 때 반드시 마이그레이션을 거치게** 하려는 것이다. `text`면 오타가 그대로 새 카테고리가 된다.

### 판매 상태와 노출 여부는 다른 축이다 ★

```sql
status     product_status not null default 'active'   -- active | sold_out
is_active  boolean not null default false             -- 공개 여부
```

옛 쪽 타입에 *"is_active=노출여부와 혼동 주의"*라고 적혀 있었다. 둘은 섞이기 쉬운데 **섞으면 안 된다.**

|                              |                                          |
| ---------------------------- | ---------------------------------------- |
| **품절인데 보여야 한다**     | 있었다는 것을 알려야 재입고를 기다린다   |
| **팔 수 있는데 감춰야 한다** | 사진이 아직 없거나 공개 시점을 맞추는 중 |

`is_active`의 기본값이 **`false`(감춤)**인 것이 중요하다. 실수로 만든 행이 손님에게 보이지 않는다.

### 이미지가 두 종류다

```sql
images         text[]   -- 대표·갤러리
detail_images  text[]   -- 상세 설명용
```

앞은 목록과 상세 상단에 쓰는 사진이고, 뒤는 **세로로 길게 쌓이는 스마트스토어식 설명 이미지**다. 한 배열에 섞으면 목록 썸네일에 설명 이미지가 뜬다.

## 3. product_variants

```sql
price_krw  integer not null check (price_krw >= 0),
price_usd  integer check (price_usd >= 0),   -- 센트 단위
stock      integer not null default 0,
position   integer not null default 0,
unique (product_id, name)
```

- **가격은 정수, 통화별 컬럼.** CLAUDE.md 8절 그대로다. **환율로 계산하지 않는다** — 통화마다 값을 따로 정한다. 21,000원을 환율로 바꾸면 $15.23 같은 값이 나오는데 그렇게 팔지 않는다
- `price_usd`는 null 이 될 수 있다. 해외에 안 파는 물건이 있을 수 있다
- `position`은 화면에 보이는 순서. 이름순·가격순으로 정렬하면 「작은 것부터」 같은 의도를 담을 수 없다
- 한 상품 안에서 **옵션 이름은 겹치지 않는다**

## 4. RLS — 읽기만 열고 쓰기는 닫는다

```sql
create policy products_read_public on products
  for select using (is_active = true);
```

**읽기는 누구나, 단 공개된 것만.** `is_active = false`인 행은 조회 자체가 안 된다 — 숨김 처리가 아니다.

variant 에도 같은 정책을 걸되 **딸린 상품이 공개된 경우에만** 보이게 했다. 이게 없으면 **감춘 상품의 가격이 variant 를 통해 새어 나간다.**

**쓰기는 관리자에게만 연다 (2026-09-19, `0003`).**

처음에는 「쓰기 정책을 아예 만들지 않고 관리자 작업은 secret 키로 한다」고 적어 두었다. **그것은 옛 레포를 확인하지 않고 쓴 것이라 뒤집었다** — 옛 어드민은 secret 키를 쓰지 않았고, Supabase Auth 로 로그인해 RLS 가 이메일을 보고 열어주는 구조였다 (`useAdminProducts.ts`).

계승한 쪽이 낫다고 판단한 이유 셋.

1. **secret 키를 아예 다루지 않는다.** 없는 비밀은 새지 않는다
2. **누가 바꿨는지 사람 단위로 남는다.** 키에는 사람이 없다
3. **M3 손님 로그인과 같은 Auth 를 쓴다.** 따로 만들지 않아도 된다

관리자 명단은 정책에 박지 않고 `admin_emails` 표에 둔다. 박아 두면 사람이 늘 때마다 마이그레이션을 새로 써야 한다. **그 표에는 정책을 만들지 않아** API 로 읽히지 않고, `is_admin()` 이 `security definer` 로 지나서 읽는다.

> 관리자 화면이 생기면 그때 「관리자만 쓰기」 정책을 따로 판단한다. 지금은 관리자 화면이 없으므로 **아무도 못 쓰는 상태가 가장 안전하다.**

## 5. products_public 뷰

화면은 「얼마부터인가」와 「살 수 있나」를 알아야 한다. 그걸 매번 앱에서 계산하면 규칙이 화면마다 흩어진다.

```sql
create view products_public with (security_invoker = true) as
select p.*, min(v.price_krw) as min_price_krw, ...
from products p join product_variants v on v.product_id = p.id
group by p.id;
```

- `join` 이라서 **variant 없는 상품은 나오지 않는다** (1절)
- **`security_invoker = true` 가 핵심이다.** 없으면 뷰가 소유자 권한으로 읽어 **RLS 를 우회하고 감춘 상품이 새어 나간다.** 뷰를 새로 만들 때마다 이 옵션을 확인할 것

## 6. API 키 — publishable 을 쓴다 (2026-09-16 확인)

Supabase 가 `anon`·`service_role` 키를 **2026년 말에 제거**한다. 새 이름은 `sb_publishable_*`·`sb_secret_*`이다.

**실제로 쏴서 확인했다.** 둘 다 `supabase-js` 방식(`apikey` + `Authorization: Bearer`)으로 인증에 성공한다 — 없는 테이블을 조회해 `PGRST205`(인증은 됨, 테이블 없음)가 오는 것으로 확인했다.

> 새 키는 `Authorization: Bearer` 로 못 보낸다는 글이 있으나 **이 프로젝트에서는 동작했다.** 문서가 아니라 실측이 기준이다.

`.env.local` 과 Vercel 환경변수에 **publishable 키를 넣는다.** anon 키는 쓰지 않는다 — 지금 쓰면 올해 안에 다시 바꿔야 한다.

**secret 키는 저장소에도 이 문서에도 두지 않는다.** 필요해지면 Vercel 환경변수에 직접 넣는다.

## 7. 사진은 Storage 에 둔다 (2026-09-16)

처음에는 사진이 레포 안(`public/photos/`)에 있었다. 그 방식은 **사진 한 장을 추가할 때마다 코드를 고쳐 배포해야 한다.** 상품이 늘면 못 버틴다.

### 버킷

`product-images`, **공개 버킷**이다. 상품 사진은 감출 것이 아니고, 공개여야 `/storage/v1/object/public/...` 주소로 바로 받을 수 있다. 서명 주소는 만료가 있어 CDN 캐시와 `next/image` 에 얹기 나쁘다.

쓰기는 **관리자에게만 연다** (`0003`). `products` 와 같은 규칙이다 — 로그인하지 않은 publishable 키로는 못 올린다. 대시보드 업로드는 secret 권한으로 움직이므로 정책과 무관하게 올라간다.

### DB 에는 경로만 넣는다 ★

`images[]` 에 **전체 주소를 넣지 않는다.** 저장소 안의 경로만 넣는다.

```
images: ['flower-bead-keyring/01.jpg', 'flower-bead-keyring/02.jpg']
```

전체 주소를 넣으면 **프로젝트가 바뀔 때 모든 행을 고쳐야 한다.** 경로만 두면 `src/lib/images.ts` 한 군데를 고치면 끝난다.

`imageUrl()` 이 주소를 만든다. **이미 완성된 주소(`https://`)나 레포 안의 절대경로(`/photos/...`)는 그대로 통과시킨다** — 옮기는 동안 둘이 공존한다.

### 폴더는 slug 로 나눈다

```
product-images/
  flower-bead-keyring/01.jpg
  flower-bead-keyring/02.jpg
```

상품별로 묶이고 번호로 순서가 정해진다. 한 폴더에 전부 쌓으면 어느 상품 것인지 알 수 없고 이름이 겹친다.

### 올리는 법

1. 대시보드 → **Storage** → `product-images`
2. slug 이름으로 폴더를 만들고 사진을 올린다
3. 상품 행의 `images` 에 **경로만** 넣는다 (`flower-bead-keyring/01.jpg`)

> ⚠️ 사진을 올리는 것만으로는 화면에 안 나온다. `images` 에 경로를 넣어야 연결된다.

## 7-2. 입력값 정책 (2026-09-19, `0004`)

지금까지 아무 제한이 없었다. 가격에 `999999999` 도, 이름에 1만 자도 들어간다. 이나래가 어드민을 써보고 「최대·최소 정책이 있어야 할 것 같다」고 한 것이 이것이다.

**화면에서만 막으면 소용없다.** 화면의 검사는 우회할 수 있고 DB 의 검사는 못 한다. 그래서 **`CHECK` 제약이 기준이고 폼은 그것을 따라 적은 것**이다. 값이 어긋나면 폼이 아니라 제약을 고친다.

| 값               | 제한                           | 왜                                        |
| ---------------- | ------------------------------ | ----------------------------------------- |
| `slug`           | 영문 소문자·숫자·하이픈 3~60자 | 주소이자 **저장소 폴더 이름**이다 (7절)   |
| `name`           | 공백 제외 1~100자              | 비어 있으면 목록에서 빈 칸이 된다         |
| `name_en`        | 100자                          |                                           |
| `description`    | 2000자                         | 붙여넣다 만 글을 막는다                   |
| `images`         | 10장                           | 상세가 세로로 한없이 길어지는 것을 막는다 |
| `detail_images`  | 20장                           | 여기는 길어도 되는 자리다                 |
| `tags`           | 20개                           |                                           |
| 옵션 `name`      | 공백 제외 1~40자               |                                           |
| 옵션 `price_krw` | 0 ~ 10,000,000                 | 아래쪽은 이미 `0001` 에 있었다            |
| 옵션 `price_usd` | 0 ~ 1,000,000 (센트)           |                                           |
| 옵션 `stock`     | 0 ~ 9,999                      |                                           |
| 옵션 `position`  | 0 ~ 99                         | 음수가 들어가면 정렬이 뒤집힌다           |

slug 의 정확한 모양은 마이그레이션에 있다 — **하이픈으로 시작하거나 끝날 수 없다.**

**넉넉하게 잡았다.** 좁게 잡으면 언젠가 정상적인 물건이 막힌다. 여기서 막는 것은 「있을 수 있는 값」이 아니라 **「손이 미끄러진 값」**이다 — 붙여넣다 만 설명, 사진 100장.

> ⚠️ **0 을 하나 더 친 가격(119,000 → 1,190,000)은 통과한다.** 그것까지 막으려면 상한을 현실적인 값으로 좁혀야 하는데, 그러면 비싼 물건이 막힌다. **그건 사람이 본다.**

**옵션 개수(1~20)만 폼에서 막는다.** 「행이 몇 개인가」는 `CHECK` 로 쓸 수 없고 트리거가 필요한데, 옵션이 없는 상품은 어차피 `products_public` 뷰가 걸러내서 화면에 안 나온다 (5절). 상한은 실수를 막는 용도라 폼이면 충분하다.

## 7-3. 주문 (2026-09-19 설계, `0005`)

**옛 레포에 설계가 이미 있었다** — [`docs/design/checkout-data-model.md`](https://github.com/jerryko570/butter-weather-shop/blob/main/docs/design/checkout-data-model.md) (2026-07-08). 그것을 계승한다.

```
orders (영수증 표지) 1 ─< order_items (줄들) N
                          └ product_id → products      (지금 사진은 이어 본다)
                          └ variant_id → product_variants
```

### 박제가 이 설계의 이유다 ★

`order_items` 는 주문 시점의 **이름 · 옵션 이름 · 단가**를 복사해 들고 있다.

**나중에 상품 이름이나 가격이 바뀌어도 영수증은 그때 그대로여야 하기 때문이다.** 가격을 `products` 에서 조인해 오면 어제 산 사람의 영수증 금액이 오늘 달라진다.

**바뀌어도 되는 것만 이어 본다** — 사진이 그렇다. 그래서 `product_id` · `variant_id` 는 남기되 `on delete set null` 이다. 상품을 지워도 영수증은 남는다.

### 회원만 산다 (확정)

`orders.user_id` 는 `not null` 이다. 구글·카카오 OAuth 로 들어오므로 **가입이라는 단계가 따로 없다** — 누르면 1~2초에 끝난다.

비회원 주문을 허용하면 「주문을 무엇으로 찾을 것인가」(주문번호+전화번호 같은 것)를 따로 만들어야 하는데, 그 값어치가 OAuth 한 번보다 크지 않다고 봤다.

**배송지는 회원 정보에서 끌어오지 않고 주문할 때 받는다.** OAuth 는 이름과 이메일만 주고, 주소는 어차피 주문마다 다를 수 있다. `shipping_info` jsonb 에 담는다.

`agree_privacy` 는 `check (agree_privacy)` 로 **참이어야만 행이 들어간다.** 전자상거래법상 필수라 「깜빡하면 null 로 들어가는」 자리를 두지 않았다.

### 재고는 결제 완료 때 깎는다 (확정)

옛 설계에도 미결로 남아 있던 것이다. 셋 중 이것을 골랐다.

|                     | 문제                                          |
| ------------------- | --------------------------------------------- |
| 담을 때             | 안 사고 나간 사람의 재고가 묶인다             |
| 주문 생성 때 + 만료 | 정확하지만 만료를 따로 만들어야 한다          |
| **결제 완료 때** ✅ | 결제 직전까지 남이 살 수 있다 — 지금은 괜찮다 |

지금은 주문이 동시에 몰리는 상황이 아니고 재고도 소량이다.

**그래도 조건부로 깎는다.** `mark_order_paid()` 가 `where stock >= quantity` 로 빼고, **0행이 바뀌면 그것이 곧 「재고 없음」**이다. 읽고 나서 빼면 그 사이에 남이 사 갈 수 있는데 조건부 update 는 그 틈이 없다. 공짜로 얻는 안전이라 안 쓸 이유가 없다.

**한 줄이라도 모자라면 전체가 되돌아간다.** 함수 안에서 예외를 던지면 트랜잭션이 통째로 취소되므로 절반만 깎인 상태가 남지 않는다. 화면에는 **어느 상품의 어느 옵션이 모자랐는지**가 전달된다(`OUT_OF_STOCK:상품명 옵션명`).

`mark_order_paid()` 는 **손님이 직접 못 부른다.** 결제가 실제로 됐는지는 서버만 안다 — 결제사 통지를 받은 서버가 secret 키로 부른다.

### 배송비 (2026-09-21, `0006`)

값은 옛 사이트에 걸려 있던 것 그대로다 — **3,000원, 상품 합계 50,000원 이상이면 무료** (7절 `Shipping & Returns` 탭과 같아야 한다).

세 칸으로 나눠 둔다.

| 칸                 | 뜻                              |
| ------------------ | ------------------------------- |
| `items_krw`        | 상품 합계. **무료 판정의 기준** |
| `shipping_fee_krw` | 주문 시점의 배송비              |
| `total_krw`        | 손님이 내는 총액 = 위 둘의 합   |

**`total_krw` 의 뜻이 `0006` 에서 바뀌었다** — 전에는 상품 합계였다. 영수증에 찍히는 숫자가 「손님이 내는 돈」이라 그쪽으로 옮겼다. 기존 행은 배송비가 0 이라 값이 그대로 맞다.

**무료 판정은 상품 합계 기준이다.** 배송비를 더한 값으로 판정하면 「배송비 때문에 무료가 되는」 이상한 일이 생긴다.

**규칙은 `src/lib/shipping.ts` 한 군데에만 있다.** 화면과 서버가 같은 함수를 부른다 — 따로 세면 손님에게 보여준 금액과 저장되는 금액이 달라지고, 그것은 그대로 분쟁이다. **다만 저장되는 값은 서버가 센 것이다.** 화면이 보낸 배송비를 받지 않는다(가격과 같은 이유).

`shipping_fee_krw` 는 **박제다.** 나중에 규칙이 바뀌어도 이미 나간 영수증의 배송비는 그대로다.

### RLS

| 표            | 손님                             | 관리자 |
| ------------- | -------------------------------- | ------ |
| `orders`      | 자기 것 **읽기·만들기**          | 전부   |
| `order_items` | **부모 영수증이 자기 것일 때만** | 전부   |

**손님은 주문을 고치거나 지우지 못한다.** `update`·`delete` 정책을 만들지 않았다. 취소는 관리자가 `status` 를 바꾸는 것이다.

`order_items` 의 조건이 부모를 확인하는 이유는, 안 그러면 **`order_id` 만 알면 남의 주문 내역이 새어 나가기** 때문이다.

### 결제사를 스키마가 고르지 않는다

`payment_provider` · `payment_id` 두 칸뿐이다. 무엇을 쓸지 아직 미정이고(CLAUDE.md 1절) 둘 이상을 붙일 수도 있다. **스키마가 결제사를 알 이유가 없다.**

### 주문번호는 `YYMMDD-NNNN` 이다

`id` 가 uuid 라 손님에게 「주문번호 알려주세요」 하기 나쁘다. 부를 수 있는 번호를 따로 둔다.

```
260919-0007     ← 2026-09-19 의 7번째 주문
```

이나래가 처음 제안한 것은 `yyyymmddhhmmss` + 순번이었다. 그러면 17자리가 되어 전화로 불러주기 어렵고, **초까지 넣어도 순번은 여전히 필요하다** — 같은 초에 둘이 들어오면 겹치기 때문이다. **유일성을 만드는 것이 순번이라면 초는 자리만 차지한다.**

날짜가 보여서 문의 응대에 바로 쓰이고 정렬도 시간순이다. 대신 **하루 주문량이 노출된다** — 「오늘 7번째 손님」이 보인다. 꺼려지면 순번 대신 무작위 네 자리를 넣으면 되지만 정렬을 잃는다.

만드는 방식에서 두 가지를 조심했다.

- **날짜는 한국 시각이다.** Postgres 의 `current_date` 는 UTC 라 그대로 쓰면 **한국 시각 0시~9시 주문이 전날 번호**를 받는다
- **번호는 트리거가 붙인다.** column default 로 두면 손님이 함수 실행 권한을 가져야 하고, 무엇보다 **손님이 값을 같이 보내면 그것이 이긴다** — 번호를 손님이 정하게 되는 셈이다. 트리거는 보낸 값을 덮어쓴다

세는 것은 `order_number_counters` 표의 upsert 한 문장이다. 읽고 나서 1을 더하는 방식이었다면 그 사이가 틈이 된다.

### 아직 안 한 것

- **배송 추적** — 송장번호 자리가 없다. I3.4 관리자향에서 붙인다
- **부분 취소·환불** — `status` 가 주문 전체 단위다. 줄 단위 취소가 필요해지면 구조가 바뀐다
