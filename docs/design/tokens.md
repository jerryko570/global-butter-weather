# Design Token 사용 규약

> **2026-09-07 작성.** `src/app/styles/`에 이미 있는 token을 **언제·어디에 쓰는지** 정한다.
> token 자체를 새로 만드는 문서가 아니다 — 값을 하나 더 얹기 전에 반드시 이 문서를 먼저 갱신할 것.
> 근거는 [brand/foundation.md](../brand/foundation.md) 5-8절 「틀과 알맹이」다. 이 문서는 그 원칙을 코드 레벨의 판단으로 내린 것이다.

## 0. 파일 구조

| 파일                    | 무엇                               | 이 문서의 |
| ----------------------- | ---------------------------------- | --------- |
| `styles/theme.css`      | 진입점. 아래 셋을 `@import`만 한다 | —         |
| `styles/colors.css`     | 색 + 다크모드 반전                 | 2절       |
| `styles/typography.css` | 서체·글자 크기                     | 3절       |
| `styles/layout.css`     | 화면 폭·높이, 모션                 | 4·5절     |

색을 바꾸는 것은 브랜드 판단이라 따로 보는 일이 잦다. 그래서 한 파일에 섞지 않고 나눠 둔다. `@theme inline` 블록은 파일마다 따로 있어도 Tailwind가 하나로 합친다.

## 1. 왜 필요한가

5-8절은 "틀은 조용하게, 알맹이는 포인트로"라는 **원칙**을 세웠다. 그런데 실제로 component를 만들 때마다 "이 텍스트는 `ink`인가 `ink-muted`인가", "이 배경은 `cloud`인가 `gray-50`인가"를 매번 새로 판단하면 사람마다 다르게 짠다. 이 문서는 그 판단을 미리 내려서, **코드를 짤 때는 고민하지 않고 표만 보게** 한다.

## 2. 색

### 2-1. 의미 token vs grayscale — 가르는 기준

`colors.css`에 두 계열이 따로 있다. 헷갈리기 쉬워서 기준을 명확히 한다.

|                                                       | 무엇                                                                             | 언제 쓰나                                                                                  |
| ----------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **의미 token** `cloud` `ink` `ink-muted` `ink-subtle` | 다크모드에서 **반전되는** 값                                                     | 배경·본문 텍스트처럼 라이트/다크에 따라 값이 달라져야 하는 곳. **거의 항상 이쪽이다**      |
| **grayscale** `gray-50`~`gray-950`                    | 다크모드에서도 **같은 자리를 지키는** 스케일(라이트의 50은 다크의 950과 같은 값) | 카드 배경·구분선·hover 배경처럼, 의미 token 다섯 개로는 부족한 **중간 단계**가 필요할 때만 |

**판단 순서: 의미 token으로 되면 그것부터 쓴다. grayscale은 의미 token에 없는 중간 톤이 필요할 때만 예외로 쓴다.** 본문 텍스트에 `gray-800`을 쓰지 않는다 — 그건 `ink`다.

### 2-2. 배경·텍스트

| 자리                                | class                               | 비고                                                                                                                                                                                            |
| ----------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 페이지 배경                         | `bg-cloud`                          | `body`에 이미 적용됨. component에서 다시 얹지 않는다                                                                                                                                            |
| 본문 텍스트                         | `text-ink`                          | 기본값. `body`에 이미 적용됨                                                                                                                                                                    |
| 보조 텍스트                         | `text-ink-muted`                    | 설명·caption·부제. `foundation.md` 캐치 문구 아래 문장 등                                                                                                                                       |
| 비활성·placeholder                  | `text-ink-subtle`                   | disabled 상태, input placeholder                                                                                                                                                                |
| 카드·구획 배경 (배경과 살짝 구분만) | `bg-gray-50` (다크는 자동으로 반전) | `cloud`와 다른 배경이 필요한데 다른 "의미"는 아닐 때                                                                                                                                            |
| interactive hover 배경              | `hover:bg-gray-100`                 | 버튼·아이콘 버튼처럼 클릭 가능한 요소의 hover만. `ThemeToggle`이 첫 사례. 카드 배경과 다른 용도지만 같은 token을 쓴다 — 새 의미를 만들지 않고 이미 있는 "구분만 되는 배경" 자리를 재사용하는 것 |
| 구분선                              | `border-gray-200`                   | 진한 선이 필요하면 `gray-300`. 그 이상 진하게 가지 않는다 — 5-8절이 header에 구분선을 넣지 않은 것과 같은 이유로, 선 자체를 최소화한다                                                          |

### 2-3. 브랜드 액센트 — `butter` · `sky`

**이 둘은 포인트 전용이다. 배경으로 깔지 않는다.** (5-8절: "배경은 `--cloud`. butter를 배경으로 깔지 않는다.")

| 쓰는 곳                                                        | 안 쓰는 곳                               |
| -------------------------------------------------------------- | ---------------------------------------- |
| 작은 강조선·점·아이콘 (지금 `page.tsx`의 `bg-butter` 막대처럼) | 섹션 전체 배경                           |
| primary 버튼의 배경 (버튼 자체가 작은 면적이라 허용)           | 버튼이 화면 전체 폭을 채우는 CTA 배너    |
| 활성 상태 표시 (선택된 탭의 밑줄 등)                           | hover 배경처럼 넓은 면적에 반복되는 상태 |

**한 화면에 butter/sky 포인트는 원칙적으로 하나.** 여러 개 필요해 보이면 정말 다 강조해야 하는지 되묻는다 — 전부 강조하면 아무것도 강조되지 않는다.

`butter-light` / `butter-dark`는 `--butter` 자체의 명도 변형이다. 새로운 의미를 갖지 않는다 — hover/active처럼 상태가 바뀔 때 밝기만 다른 `--butter`가 필요한 경우에만 쓴다. 새 색을 뽑는 데 쓰지 않는다.

### 2-3-1. 액센트 위의 텍스트 — `ink-on-accent`

**butter/sky 배경 위에 얹는 텍스트는 `text-ink-on-accent`를 쓴다.** `ink`를 쓰지 않는다 — `ink`는 다크모드에서 밝은 색으로 뒤집히는데, butter/sky는 다크에서도 반전되지 않으므로(5-8절) 다크모드에서 밝은 배경에 밝은 글자가 겹쳐 대비가 사라진다.

`Button`의 `primary` variant가 첫 사례다. `colors.css`의 `:root`에만 정의돼 있고 `.dark`에서 재정의하지 않는다 — 테마와 무관하게 항상 어두운 색이어야 하기 때문이다. **이 token은 예외적으로 다크모드에서 반전되지 않는다는 것을 기억할 것.**

### 2-4. 하드코딩 금지

**hex 값을 component 코드에 직접 쓰지 않는다.** `#f5c842`처럼 쓰면 나중에 이 문서와 코드가 따로 논다. 항상 token 유틸리티(`bg-butter`, `text-ink` 등)를 거친다.

새 색이 필요하면 이 문서에 먼저 추가하고 `colors.css`에 token으로 넣은 다음 쓴다. 색을 판단하는 사람(이나래)과 코드에 반영하는 사람(홍설아)이 다르므로, token을 거치지 않으면 그 판단이 코드에 없는 채로 흩어진다.

### 2-5. 색을 섞지 않는다 ★

**그라데이션·blur·반투명 겹침을 쓰지 않는다.** 면과 면은 선명한 경계로 나눈다.

이나래가 만든 물건 33점에 그라데이션이 한 점도 없고, **의도된 것으로 확인됐다**(foundation.md 5-9절). 색은 언제나 경계를 가진 조각으로 놓이고 그 사이를 중립색(실버)이 받친다. 졸업작품이 콜라주였던 것과 같은 방식이다.

| 쓰지 않는 것                     | 대신                                    |
| -------------------------------- | --------------------------------------- |
| `bg-gradient-*`                  | 단색 면                                 |
| `backdrop-blur`, 반투명 오버레이 | 불투명한 면, 또는 여백으로 분리         |
| 색이 서서히 번지는 그림자        | 필요하면 얇은 경계선(`border-gray-200`) |

**어떤 색을 쓸지는 이 문서가 정하지 않는다.** 색 목록도, 고르는 기준도 두지 않는다 — 본인 확인이다(foundation.md 5-9절 확인됨 4). _"색은 거르는 기준도 사실은 없고, 색이 주는 유니크함이 주는 상황마다 다르게 설정될 수 있어."_

이 문서가 색에 대해 정하는 것은 **어떻게 쓰는가**(면적·자리·섞지 않기)뿐이고, **무엇을 쓰는가**는 매번 이나래가 판단한다. 새 색이 필요한 순간이 오면 고르지 말고 **묻는다.**

## 3. 타이포

서체 token은 둘이다. **`--sans`(Pretendard)가 기본**이고 `body`에 이미 적용돼 있어 대부분 아무것도 안 해도 된다. **`--serif`는 브랜드의 목소리에만** 쓴다 (아래 3-3).

### 3-1. 크기는 역할 이름으로 부른다

**`text-sm`·`text-2xl` 같은 Tailwind 기본 스케일을 쓰지 않는다.** 아래 여섯 개만 쓴다.

| class           | 크기           | 자리                                            | 서체  |
| --------------- | -------------- | ----------------------------------------------- | ----- |
| `text-display`  | 2.375rem 38px  | 히어로 제목. **한 화면에 하나**                 | serif |
| `text-title`    | 1.375rem 22px  | 구획 제목 · 지표 숫자                           | serif |
| `text-wordmark` | 0.9375rem 15px | 브랜드 표기 `BUTTER WEATHER`                    | serif |
| `text-body`     | 0.8125rem 13px | 본문 · 상품명 · 가격 · 링크. **가장 많이 쓴다** | sans  |
| `text-caption`  | 0.6875rem 11px | 버튼 · 메타 · 보조 링크                         | sans  |
| `text-label`    | 0.625rem 10px  | 대문자 소형 라벨 (`SHOP` `KEYRING`)             | sans  |

**왜 역할 이름인가.** 크기 이름(`sm`/`lg`)으로 두면 새 화면을 짤 때마다 "이 자리에 어떤 크기가 맞나"를 다시 판단하게 된다. 역할 이름이면 **자리가 정해지는 순간 크기도 정해진다.**

### 3-2. 값은 어디서 왔나 (2026-09-16 재정의)

**이전 스케일(24/18/14/12)은 버렸다.** M0 임시 화면 하나에서 뽑은 것이라 근거가 얇았고, 실제로 쓰이지도 않았다.

지금 값은 **옛 버터웨더 사이트에서 계승한 디자인이 실제로 쓰던 크기**다 (CLAUDE.md 1절). 그 디자인은 아홉 개를 썼고, 실사용 빈도로 묶어 여섯으로 줄였다.

| 원본        | 어떻게 했나                                                                        |
| ----------- | ---------------------------------------------------------------------------------- |
| 38px        | `display` 그대로                                                                   |
| 22px · 20px | `title` 22px로 합침 — 2px 차이에 역할 차이가 없었다                                |
| 15px        | `wordmark` 그대로. 쓰이는 곳은 한 군데지만 **브랜드 이름이라 값을 못박는다**       |
| 14px · 13px | `body` 13px로 합침 — 내비게이션(14)과 본문(13)의 1px 차이는 의도가 아니었다고 봤다 |
| 12px · 11px | `caption` 11px로 합침                                                              |
| 10px        | `label` 그대로. 가장 자주 쓰인다                                                   |

### 3-3. serif는 브랜드의 목소리에만 ★

**제목·지표·워드마크·태그라인은 serif, 본문·라벨은 sans.** 계승한 디자인의 핵심 성격이 이 구분이다. serif를 본문에 쓰지 말 것 — 그 순간 화면이 다른 브랜드가 된다.

> ⚠️ **어떤 serif인지는 아직 정해지지 않았다.** `--serif`는 OS에 있는 것을 주워 쓰는 대비책이라 **기기마다 다르게 보인다** — 라틴은 Georgia, 한글은 macOS에서 AppleMyungjo, Windows에서 바탕으로 떨어진다. **브랜드 제목이 사람마다 다른 얼굴로 보인다.**
>
> 옛 사이트도 같은 상태였다(`font-serif`만 쓰고 웹폰트를 안 실었다). 계승하면서 문제도 같이 왔다.
>
> **서체를 고르는 것은 이나래의 판단이다.** 고르고 나면 Pretendard처럼 `public/fonts/`에 싣고 이 token의 맨 앞에 넣는다. 8절 열린 질문 참조.

### 3-4. 자간은 역할에 묶여 있다

`text-wordmark`(0.12em)와 `text-label`(0.14em)은 **자간이 token에 포함돼 있다.** 쓸 때 `tracking-*`을 따로 적지 않는다 — 자간이 벌어져 있는 것까지가 그 역할의 생김새다.

`text-label`은 **항상 대문자와 함께 쓴다.** 소문자로 쓰면 자간만 벌어진 작은 글자가 되어 읽기 나빠진다.

`text-caption`에는 자간을 묶지 않았다. 대문자로 쓸 때만(버튼·`CART`) `tracking-widest`를 따로 얹는다.

### 3-5. 굵기

`font-medium`이 강조의 상한이다. 그보다 굵게(`font-semibold` 이상) 가지 않는다 — 본문·UI 타이포는 5-8절의 「틀」이라 조용해야 하고, 굵기로 강조하기 시작하면 화면이 시끄러워진다. 강조가 필요하면 **크기나 색**(`text-ink` vs `text-ink-muted`)으로 먼저 푼다.

계승한 디자인은 제목에 굵기를 거의 쓰지 않는다. **serif라는 것 자체가 이미 강조**이기 때문이다.

## 4. layout

| token             | 값     | 쓰는 곳                                                                                                    |
| ----------------- | ------ | ---------------------------------------------------------------------------------------------------------- |
| `--container-max` | 1280px | `max-w-(--container-max)`. 화면 폭 제한이 필요한 모든 곳 — `Header`가 첫 사례                              |
| `--header-height` | 64px   | 헤더 자체 높이. 헤더 바깥에서 "헤더만큼 밀어야 하는" 계산에도 이 token을 참조한다 (하드코딩된 `64px` 금지) |

## 5. 모션

`ease-smooth` · `duration-fast` · `duration-normal`은 정의만 있고 실제로 쓰인 곳이 아직 없다. 지금 기준을 정해 둔다.

| token               | 값                             | 쓰는 곳                                                                    |
| ------------------- | ------------------------------ | -------------------------------------------------------------------------- |
| `--duration-fast`   | 150ms                          | hover·focus처럼 손가락 아래서 바로 반응해야 하는 것                        |
| `--duration-normal` | 250ms                          | 모달 열림, 아코디언, 탭 전환처럼 상태 자체가 바뀌는 것                     |
| `--ease-smooth`     | `cubic-bezier(0.4, 0, 0.2, 1)` | 위 두 duration과 항상 같이 쓴다. 단독으로 다른 easing을 새로 만들지 않는다 |

**모션도 절제한다.** 4절 표현 원칙("설명을 많이 하지 않는다")과 같은 태도로, 화면이 스스로를 과시하는 연출(bounce, 과한 scale)은 쓰지 않는다. 상태가 바뀌었다는 것만 부드럽게 알리는 정도로 그친다.

## 6. 다크모드

`.dark` class를 수동으로 토글한다 (OS 설정 자동 추종 아님, `CLAUDE.md` 4절 참조). 의미 token·grayscale은 반전되고 `butter`·`sky`는 유지된다 — 이미 `colors.css`에 구현돼 있다.

**component를 짤 때 다크모드를 별도로 신경 쓸 필요가 없다.** 의미 token(`cloud`/`ink`/`ink-muted`/`ink-subtle`)과 grayscale만 쓰면 `.dark`가 알아서 반전한다. 위 2-4절대로 hex를 하드코딩하지 않는 한 자동으로 지켜진다.

## 7. 체크리스트 — component를 짤 때

1. 배경·텍스트에 hex를 직접 쓰지 않았는가 → 2-4절
2. 본문 텍스트에 grayscale을 쓰지 않았는가 → 2-1절 (의미 token으로 되면 그것부터)
3. `butter`/`sky`를 넓은 면적에 쓰지 않았는가, 화면에 포인트가 둘 이상 아닌가 → 2-3절
4. 애니메이션에 새 duration·easing 값을 만들지 않았는가 → 5절
5. 그라데이션·blur·반투명 겹침을 쓰지 않았는가 → 2-5절

## 8. 열린 질문

이 문서를 쓰면서 판단이 필요했지만 아직 실제 화면(component 두세 개)이 없어 근거가 약한 것들이다. 다음 `FE/*` 스토리에서 실물이 나오면 다시 확인한다.
