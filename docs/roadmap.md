# Butter Weather — 서비스 구조 & 빌드 로드맵

> 작성 2026-07-05. 시나리오(자연어 스펙)와 현재 코드 실측을 대조해 "뭘 만들어야 하는지" 정리한 문서.
> 코드가 바뀌면 이 문서도 같이 갱신할 것.

---

## 한 줄 요약

결제까지 가는 **"단일 상품 즉시구매"** 뼈대는 이미 있다.
그러나 시나리오가 원하는 건 **"장바구니에 여러 개 담아 → 주문서에서 정보 받고 → 한 번에 결제 → 마이페이지에서 배송 추적"**이다.
이건 지금 데이터 모델과 근본적으로 어긋나서, **가장 먼저 정할 건 코드가 아니라 "주문을 어떤 그릇에 담을지"다.**

---

## 목표 시나리오 (사용자 스펙)

1. 구글·카카오 간편 회원가입/로그인
2. 상세페이지에서 구매 이벤트 → **주문서 페이지**로 이동 → 이름·주소·요청사항 입력
3. **장바구니** 합구매 지원
4. 구매 완료 → 주문완료 페이지 + 이메일/알림톡 알림
5. 결제는 **포트원** 의존. 주문ID ↔ 결제ID 연결 구조
6. 사용자 상세정보는 주문/결제 완료 시점에 저장. 개인정보 동의·마케팅 동의 함께 수집
7. 마이페이지에서 주문·결제·배송 상태 조회. 어드민에서 배송·송장 입력 → 사용자 조회 + 배송사 추적

## ⭐ 가장 먼저 정해야 할 것 — "주문을 담는 그릇"

지금 코드가 실제로 쓰는 건 `purchases` 테이블 하나인데, **상품 1개짜리**다
(`product_id`, `product_name`, `quantity` 딱 한 세트). `purchase.service.ts`도 상품 하나만 insert 한다.

장바구니 합구매(#3)를 하려면 "주문 1건에 상품 N개"가 필요하다.
이건 이미 DB에 있는 `orders`(영수증 표지) + `order_items`(영수증 줄들) 구조다 — **근데 코드가 아직 안 쓴다.**
(스터디 노트 `docs/study/01-db-schema.md`의 영수증 비유 그대로.)

```
지금 코드:   purchases (상품 1개 = 주문 1개)        ← 합구매 불가
시나리오:    orders (1) ─< order_items (N)          ← 합구매 가능, DB엔 이미 있음
```

**결정: `purchases`(단일) 흐름을 `orders + order_items`(합구매)로 옮긴다.**
이게 #2·#3·#5·#6·#7을 전부 떠받치는 토대라, 이걸 안 정하면 나머지가 다 흔들린다.

## 정책 체크리스트 (법적·운영상 필수)

- [ ] **개인정보 수집·이용 동의**(필수) + **마케팅 수신 동의**(선택) — 주문서에서 분리 수집 (전자상거래법)
- [ ] **개인정보처리방침 / 이용약관** 페이지 — 결제 전 필수
- [ ] **청약철회 7일** — 상세페이지 문구엔 있음, 정책 페이지로도 필요
- [ ] **재고 차감 시점** — 결제 완료 시 `stock` 감소가 지금 없음 → 오버셀링 위험
- [ ] **비회원 주문 허용 여부** — 시나리오는 로그인 기반인데 `purchases`엔 `user_id` 없음
- [x] **결제 멱등성** — `payment_id` 유니크로 처리됨 (중복결제 방지)
- [ ] **요청사항 저장 칸** — 지금 어느 테이블에도 없음 → 주문에 컬럼 추가

## 추천 빌드 순서

1. **[토대] 데이터 모델 전환** — `purchases` → `orders + order_items`, buyer/동의/요청사항 컬럼 정리 ← **출발점**
2. **[화면] 장바구니 페이지** (#3)
3. **[화면] 주문서 페이지** — 정보 입력 + 동의 (#2·#6)
4. **[연결] 합구매 결제** — 주문서 → 포트원 (#5)
5. **[화면] 주문완료 + 이메일 알림** (#4)
6. **[화면] 마이페이지 + 어드민 송장** (#7)

> 시나리오 전체가 결국 **1번(데이터 모델)** 위에 얹힌다. 다음 스텝: 실제 `orders`/`order_items` 컬럼을
